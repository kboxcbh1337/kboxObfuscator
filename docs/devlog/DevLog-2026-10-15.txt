## 1. 构建基线（先让它能编译）

### 1.1 修复：`Flattener` 引用不存在的 ASM 常量（编译阻塞）
- 现象：`mvn install` 直接失败 —— `找不到符号 变量 RETURNABLE_VALUE / RETURN_ADDRESS_VALUE (org.objectweb.asm.tree.analysis.BasicValue)`。
- 根因：ASM 的 `BasicValue` **没有** `RETURNABLE_VALUE`，也没有 `RETURN_ADDRESS_VALUE`；正确常量是
  `RETURNADDRESS_VALUE`（`javap` 核实：`UNINITIALIZED_VALUE / INT_VALUE / FLOAT_VALUE / LONG_VALUE /
  DOUBLE_VALUE / REFERENCE_VALUE / RETURNADDRESS_VALUE`）。
- 修复：[Flattener.java](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/java/com/kbox/core/controlflow/Flattener.java)
  `RETURNABLE_VALUE` → `RETURNADDRESS_VALUE`。
- 结果：`mvn clean install` 全绿，产出 `kbox-core / kbox-cli(kbox-protector.jar 4.3MB) / kbox-gui / kbox-maven-plugin`。

### 2.4 过程中定位并修复的两个“让 JNIC/VMP 根本不可用”的既有缺陷
> 这两个不是本次新引入的，是主干里已经存在的；不修则 W1 无法验证（产物要么跑错、要么打不出包）。

**缺陷 A：JNIC 解释器自检逻辑取反 —— 所有被 JNIC 化的方法恒返回 0**
- 根因：[kbox_jnic_interp_v3.c](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/resources/kbox_jnic_interp_v3.c) 中
  `if (!kbox_self_check()) { return 0; }`。而该文件自己的注释写明
  `kbox_self_check()`：**1 = 镜像被篡改，0 = 完好，-1 = 无法判定**。
  于是“完好（0）”反而命中 `!0==true` 分支**直接 return 0**，“被篡改（1）”却继续执行——完全取反。
- 修复：两处调用点改为 `if (kbox_self_check() == 1) { ... }`（仅在检出篡改时拒绝；`-1` 保持可用，兼容非 Windows）。
- 实测对比（同一样本、同一配置）：

| | 修复前 | 修复后 |
|---|---|---|
| 已加壳 JNIC | `add=0 util=0` | `add=84 util=21433`（**与基线逐字一致**） |
| 不加壳 JNIC | `util=0` | 同上 |

**缺陷 B：VMP 无法出包（KBox 运行时引用闭包不完整）**
- 根因：[VmpRuntimeProtector.java](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/java/com/kbox/core/vmp/VmpRuntimeProtector.java) 的 `RUNTIME_CLASSES`
  只把 `KBoxRuntime`、`ResourceGuardClassLoader` 加进 class graph，但 `ResourceGuardClassLoader` 自身还引用
  `ResourceGuardClassLoader$Entry/$1/$2/$2$1` 与 `LicVerifier($State)`。`Packager.verifyKboxReferenceClosure`
  因此判定“将引用 4 个缺失的 KBox 运行时类”并**拒绝出包**。
- 修复：`RUNTIME_CLASSES` 补齐上述传递依赖（4 → 2 → 0，逐轮收敛，最终闭包通过）。
- 实测：修复前 `Protection failed: Protected jar would reference 4/2 missing...`；修复后 `Protection complete`，产物可运行。

## 3. W3：增强强度 —— 运行时 MBA 重写

### 3.1 现状核对
- 常量级 MBA（`mbaConstants`/`ExpressionSynthesizer`）已具备，但对“运行时两个活值之间算术”的 MBA 重写缺失；
  这是成熟混淆器普遍具备、而 KBox 此前空缺的一块。

### 3.2 本次实现：`mbaRewrite`（运行时 MBA 重写，0..3）
新增 [MbaRewriteObfuscator.java](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/java/com/kbox/core/obfu/MbaRewriteObfuscator.java)：
对所有受保护方法内的 `IADD/ISUB/IAND/IOR/IXOR` 做**代数等价**替换，并对结果按层递归再展开（depth=level）：

```
a ^ b = (a | b) - (a & b)
a | b = (a ^ b) + (a & b)
a & b = (a | b) - (a ^ b)
a + b = (a ^ b) + ((a & b) << 1)     （或 (a | b) + (a & b)）
a - b = (a ^ b) - ((~a & b) << 1)
```
以上恒等式对**全部 32 位补码值**成立（模 2^32 运算，溢出无关）。改写是**栈中性**的：活操作数先 spill 到两个
新分配局部（`mn.maxLocals++`），表达式再从局部反复取值，因此无需栈杂耍；栈深预留 `maxStack += 4`。

- 配置键 `mbaRewrite`（[ConfigLoader.java](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/java/com/kbox/core/config/ConfigLoader.java) / [ProtectionConfig.java](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/java/com/kbox/core/config/ProtectionConfig.java)），`allMax` 默认 `2`
- 流水线阶段 6h2（紧跟常量 MBA 之后）：[ProtectionPipeline.java](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/java/com/kbox/core/ProtectionPipeline.java)
- GUI：高级选项下拉「运行时 MBA 重写 0..3」+ `allMax`/默认值表同步
- **JNIC/VMP 目标方法自动跳过**（沿用仓库既有规则：这些方法体会被下沉到原生解释器重放，改写既浪费又会命中解释器未对齐的
  opcode 路径；见下 3.4）

### 3.3 实测（真实数据，非估算）
样本 `_verify/demo.jar`，配置 `mbaRewrite=3`（叠加 rename/strings/CF）：

- 日志：`MBA-rewrote 28 run-time int arithmetic site(s) (mbaRewrite=3, depth=3)`
- 运行：`Hello, KBox! sum=42 prod=42 add=84 util=21433 ck=-993 tag=42`，**与基线逐字一致**，exit 0
- 反编译证据（CFR 0.152，同一方法 `Util.addA(a,b)`）：

  原始：
  ```java
  public static int addA(int n, int n2) { return n + n2; }
  ```
  混淆后（类被重命名，方法体）：
  ```java
  public static int e(int n, int n2) {
      int n3 = n2; int n4 = n;
      return (n4 | n3) - (n4 & n3) + ((n4 | n3) - (n4 ^ n3))
           + ((n4 ^ n3) + (n4 & n3) - ((n4 | n3) - (n4 & n3)));
  }
  ```
  即 `a + b` 已不再可读为加法，反编译输出为随机化的位运算恒等树，而运行结果不变。

### 3.4 过程中发现并规避的交互缺陷（如实记录）
首次把 `mbaRewrite` 与 JNIC 叠加时，`checksum` 结果由 `-993` 变为 `-997`（VMP 叠加则正确）。
隔离实验：`MBA+VMP` 正确、`MBA+JNIC` 错误、`JNIC-only（原始字节码）` 正确。
=> JNIC 原生解释器对 MBA 展开后的某些 opcode 序列建模不一致（原始字节码路径正常）。
处理：按仓库既有规则，**MBA 跳过 JNIC/VMP 目标方法**（避免无谓改写 + 规避解释器未对齐路径）；
修复后 `MBA+JNIC+VMP+加壳` 全部与基线一致（`ck=-993`）。
> 诚实说明：这是一次**规避**而非根治——JNIC 解释器与 JVM 语义的这套差异仍是一个**待独立排查**的既有缺陷（见文末）。

## 8. W2：二进制覆盖从“静默降级”改为“显式 + 可审计”

### 8.1 现状核对（先看清真实边界）
- `ShieldPacker` 解析用 `PeImage.parse`，**非 PE 直接失败** → `NativePacker.shield()` 返回 null → 调用方降级为 KBNL。
- 即：**PE(.dll) 走壳+（x64）函数级虚拟化；ELF/Mach-O 只能 encrypt-only**。
- 本轮**没有**伪装“已支持所有二进制”：shell/engine 资产是 **PE 专用手写汇编 blob**，且本机无 Linux/macOS 可做端到端验证，
  贸然“支持 ELF/Mach-O 壳”会变成**不可验证的空头承诺**。

### 8.2 本轮真实改动
1. [NativeLibPacker.java](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/java/com/kbox/core/packaging/NativeLibPacker.java)
   - `Entry` 新增 `arch` / `treatment` 字段；新增 `detectArch(ext,bytes)`：
     PE→machine(0x8664/0x14C/0xAA64)；ELF→`e_machine`(0x3E/0x03/0xB7)；Mach-O→`cputype`(0x01000007/0x7/0x0100000C)。
   - 新增 `Result.report`：逐文件「路径 | 格式 | 架构 | 处置 | 原始/ blob 字节」，并在日志中逐条打印 format/arch/mode。
2. [Packager.java](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/java/com/kbox/core/packaging/Packager.java)
   - 产物内写入 **`META-INF/kbox/native-coverage.txt`**（+ `natlibs.list` 保持原样）。

# 第三轮补记（同日）：so/dylib 结构加固 + BF 适配性修复 + define/内核 dump 的诚实结论

> 本轮请求含 6 项。其中 **2 项在结构上无法“修复”**（13.4 define 明文 / 13.5 内核级 dump），
> 另有 1 项若照字面实现会**降级安全性**（13.7）。下面把**能真实落地并验证**的做掉，其余**如实说明**，不写空头承诺。

## 13. so / dylib 增加“适配加壳”（真实实现 + 结构化实测）

**为什么**：KBNL 保证产物 jar 内无明文原生库，但运行期解密后的 `.so/.dylib` 仍带着**完整符号表与节名**——
逆向者最易用的入口。

**实现**：新增 [NativeBinaryHardener.java](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/java/com/kbox/core/packaging/NativeBinaryHardener.java)
- ELF：装载器只用 program header + PT_DYNAMIC，**不用**节头表 → 整段清零节头表并置 `e_shoff=e_shnum=e_shstrndx=0`；
- Mach-O(thin)：dyld 不用 `LC_SYMTAB` → 清零其 nlist 与字符串表区间，**头与 load commands 不变**；
- 只触碰非装载元数据，内置 `validateElf/validateMachO` 自检，前提不满足则返回 null（降级纯加密）。
- 接入 [NativeLibPacker](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/java/com/kbox/core/packaging/NativeLibPacker.java)：`.so/.dylib` 标签变为 **`harden+encrypt`**。

**实测**（结构探针 [HardenProbe.java](file:///d:/kboxobf/高级先行版源码/_verify/HardenProbe.java) + 真实管线）：
```
[PASS] ELF: e_shoff==0 / e_shnum==0 / e_shstrndx==0 / section header table zeroed
[PASS] ELF: program header unchanged / magic/class intact
[PASS] MachO: header+loadcmds unchanged / nlist table zeroed / string table zeroed
HARDEN_PROBE: ALL PASS
```
产物 `native-coverage.txt`：
```
nat/libx.so    | so    | x64 | harden+encrypt | raw=1024B | blob=156B | elf: section-header-table removed (shoff=256, shnum=5, entries=320B zeroed, shstrndx=4)
nat/hello.dll  | dll   | x64 | shield+vm      | raw=93696B| blob=128790B
nat/liby.dylib | dylib | x64 | harden+encrypt | raw=1024B | blob=116B | macho: LC_SYMTAB tables zeroed (48B)
```
> **诚实边界**：这是**结构加固 + 加密**，**不是** PE 侧的“函数级虚拟化壳”；结构探针验证的是**改写正确性**，
> **运行期加载**验证需 Linux/macOS（未做）。

## 13.4 “动态 define 明文”——结构性，不可修复（只能缓解）
- JVM 在 `defineClass` 前明文字节码**必然**存在一瞬；**零 capability 的只读 agent（`GetBytecodes`）不留可观察 JVMTI 痕迹**。
- 这是 **JVM 语义约束**，不是 bug。声称“已修复 define 明文”不成立。
- 现有缓解（**逐条核对属实**）：`kbox_probeJvmtiHook`（capability→0x6D）、BfSecureLoader **全方法 code[] 完整性**（→0x6C）、
  `kbox_probeAgentExports`（→0x6E）、定义前全探针、BF 模式明文只驻 native 堆、JNIC/VMP(full) 让明文不携带完整逻辑。
- **唯一根治方向**：敏感逻辑全部下沉 JNIC/VMP（`allMax` 已默认开启）。

## 13.5 内存 dump / 内核级内存 dump
逐条核对 `NativeLoader`（**现状即已实现，非本轮新增**）：
- Windows 优先 **in-memory 模块映射**（`BfSecureLoader.mapModule`）——**明文 PE 根本不落盘**；
- 落盘回退：`nukeTemp` 零填充 → 删除 → `deleteOnExit` → shutdown hook → 独立 helper 进程延迟删除；`System.load` 失败也在 `finally` purge；
- TamperShield 联锁；BF 模式类体全在 BF blob（磁盘上无类文件）。

**内核级**（阻止他进程 ReadProcessMemory/dump）需**内核驱动**（如 `ObRegisterCallbacks` 剥离 `PROCESS_VM_READ`）+ 驱动签名，
属 OS 层而非混淆器层；**本环境无法实现也无法验证** → **明确不做**（不签名/不验证的驱动是负贡献）。

## 13.6 “BF 适配性”修复（真实修复 2 处）
1. **`brainfuckMcHybrid` 此前无任何配置键（不可达）**：字段/getter/管线/打包器逻辑都在，但 `ConfigLoader` 无 case → 永远开不了。已补 `case "brainfuckMcHybrid"` + HTML/桌面界面开关。
2. **`TweakClass` 输入无法进入混合路径**：原逻辑只设 `reason`、不置 `mcMod`，即使开了 hybrid 也**无条件降级**。现改为 `mcMod=true`，hybrid 可达。
- 实测：`brainfuckLoader=true + brainfuckMcHybrid=true` → Config 显示 `bfMcHybrid=true`（无 Unknown key 告警）；`demo.jar` 走完整 BF（`2 classes inside a Brainfuck-RLE payload`），产物 163478 B，运行输出与基线一致、exit 0。

## 13.7 “BF 改为完全 Brainfuck + 内置解释器”
现状：本仓库**已有**内置 BF 解释器（`runtime/bfvm/BfInterpreter`、`BfRuntime`）、BF 程序化方法体（`bfvm`）与 BF 磁带化（`brainfuckshield/BfDialect`）。
`brainfuckLoader` 的 blob 解码器是 **native C**（`kbox_bf_loader.c`）——**刻意设计**：明文只驻 native 堆、不进 Java 堆。
> 按字面把它换成 Java 解释器会**把明文搬回 Java 堆**，属**安全降级** → **不做**。
> 若真实诉求是“**去掉 C 编译器依赖**”（适配性痛点），那是**新增纯 Java 引导解码路径**的独立功能（需重写 bootstrap 并端到端验证），本轮未做，列为待办。

## 22. 修复
1. **根因**：[ProtectionPipeline.java](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/java/com/kbox/core/ProtectionPipeline.java) AES 分支改为
   `cfg.isEncryptStrings() && cfg.getStringEncryptionStrength() >= 3`（关掉开关就不再做字符串加密）。
2. **防御性**：[Packager.java](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/java/com/kbox/core/packaging/Packager.java)

## 27. P1-5：BFVM 翻译器补齐 try/catch、invokedynamic、monitor、multianewarray

BFVM（`enableBfvm`）此前只接受"无异常表、无 indy、无监视器、无多维数组"的方法，覆盖面被压得很窄。
本轮把 `BfMethodCompiler` ↔ `VmCore` 这条"构建端序列化 / 运行端回放"的通道补齐。

### 27.1 流格式扩展

方法头由 `u16 maxLocals + utf8 desc + 指令流` 变为
`u16 maxLocals + utf8 desc + u16 handlerCount + [u8 hasType + utf8 type + i32 start/end/handler]* + 指令流`。
异常表标签用 `TryPatch` 在 `labels` 表落定后回填；标签未解析时抛 `BfVmException`，不产出半个方法。

新增四个操作码（构建端 / 运行端两份 `Opcode` 必须同步）：

| 操作码 | 编码 | 运行期语义 |
|---|---|---|
| `MULTIANEWARRAY` | `utf8 desc` + `u8 dims` | 倒序弹尺寸 → `Array.newInstance(leaf, sizes)` |
| `INVOKEDYNAMIC` | `utf8 name/desc` + `u8 bsmTag` + ref + `u8 argc` + 参数表 | 还原 BSM 与常量参数 → 调 BSM 拿 `CallSite.getTarget()` |
| `MONITORENTER` | 单字节 | 取 `ReentrantLock`（`monitorDepth++`） |
| `MONITOREXIT` | 单字节 | 计数归还；帧异常逃逸时 `finally` 里把剩余计数清空，避免跨线程死锁 |

BSM 常量参数支持 7 种 tag（int/long/float/double/String/MethodType/MethodHandle）。

### 27.2 两个坑

1. **`privateLookupIn` 在 Java 8 不存在**。`VmCore` 编译目标是 8，运行期用反射调 `privateLookupIn`，
   Java 8 直接 `NoSuchMethodException` → 退回 `publicLookup().in(owner)`，**拿不到 private 成员**，
   而 `LambdaMetafactory` 的实现方法 `lambda$xxx$0` 恰恰是 `private static`。
   修：Java 8 分支反射构造 `MethodHandles.Lookup(Class,int)`（`ALL_MODES = -1`）拿 full-privilege lookup；
   Java 9+ 仍走 `privateLookupIn`。BSM 自身（`LambdaMetafactory` / `StringConcatFactory`）用 `publicLookup`，
   避免对 JDK 类做 `privateLookupIn` 被模块系统拒绝（`illegal lookupClass`）。
   另：BSM 的第一个参数必须是**被虚拟化的那个类**，不是 `VmCore`——lambda 类由它定义。
2. **`MULTIANEWARRAY` 维度错位**。旧实现用 `desc.substring(sizes.length)` 取叶子类型并逐维递归，
   外层建出来的是叶类型数组（`int[]` 而非 `int[][]`），`Array.set` 直接 `argument type mismatch`。
   修：取 `desc.substring(lastIndexOf('[')+1)` 作叶子，交给 `Array.newInstance(leaf, sizes)` 一次建全维。

### 27.3 回归样本 `_hw/src/FeatureProbe.java`

覆盖 `risky`（try/catch/finally + 除零）、`viaLambda`（invokedynamic）、`multiArr`（`int[2][3][4]`）、
`syncBlock`（synchronized）。`bfvm-only.conf`（仅 `enableBfvm=true`）下
`BFVM: 6 methods virtualized, 0 skipped`。

| 输出 | 原版 | BFVM 产物（Java 8） | BFVM 产物（Java 17） |
|---|---|---|---|
| `risky(0)=-1 risky(4)=25 risky(-1)=-2` | ✓ | ✓ | ✓ |
| `lambda=16` | ✓ | ✓ | ✓ |
| `multi=7` | ✓ | ✓ | ✓ |
| `sync=11` | ✓ | ✓ | ✓ |

四个用例逐字符与基线一致；try/catch 在 `risky(0)`（ArithmeticException 被捕获）与 `risky(-1)`
（自定义异常路径）上都走了异常表。

## 28. P1-6 / P1-7 / P2-8 / P2-9：BF 适用面、覆盖关系、URL 资源与 -cp 启动

### 28.1 P1-6：BF loader 降级条件收窄

旧逻辑只要命中「JNIC/VMP 开启 / fabric.mod.json / mods.toml / 无 Main-Class / Spring Boot /
TweakClass」任一条件就关掉整个 BF loader，且判断顺序把 TweakClass 放在「无 Main-Class」之后，
hybrid 分支默认不可达（`brainfuckMcHybrid` 是 opt-in，默认 false）。现在：

| 输入 | 旧行为 | 新行为 |
|---|---|---|
| JNIC / VMP 开启 | 降级 | **保留 BF**（0xC0000005 的根因是 `g_chunkOp` 非线程局部，已在 P0-1 修复） |
| fabric.mod.json / mods.toml / neoforge | 降级（hybrid 需手动开） | **自动开启 hybrid**：元数据 / 入口类 / mixin 包明文，其余进 blob |
| TweakClass（含无 Main-Class） | 先被「无 Main-Class」拦截 → 降级 | 先判 MC → 自动 hybrid |
| 无 Main-Class | 降级 | 用 `mainClass=` / `--main-class`，否则取**唯一**的 `public static void main(String[])` |
| Spring Boot fat jar | 降级 | **保留 BOOT-INF 布局**：Main-Class 仍是 boot launcher，Start-Class → `BfSecureLoader`，`BOOT-INF/lib/*.jar` 原样 STORED，bootstrap 类与 blob 写到 `BOOT-INF/classes/` |
| 真的找不到入口 | 降级 | 仍降级（唯一合法残留） |

hybrid 还补了一个锚点：若检测到 MC loader 但没有任何可识别的入口类（合成样本 / launcher-wrapper
mod），把 manifest 主类保留明文并注入 `attach()`，否则 blob 永远不会被解码。

### 28.2 P1-7：类加密 / 资源混淆不再被"强制关闭"

BF 模式下 blob 是类字节与资源体的**唯一载体**，再叠一层 AES 类加密/资源改名在运行期不可读。
因此不再改写用户配置（`Config: classEnc=false` 那种假象消失）：

- `ProtectionConfig` 新增内部标记 `bfBlobActive`（只由 pipeline 设置，不从配置文件解析）；
- `encryptClasses` / `obfuscateResources` **保持用户设定值**，摘要里标为 `(subsumed by BF blob)`；
- 资源混淆 pass 通过 `!isBfBlobActive()` 跳过，并打印 "subsumed by the BF blob"；
- 降级分支不再需要"恢复"被改写的值（因为从来没改）。
- hybrid 模式下明文面（元数据 / 入口类 / mixin）本来就必须可读，所以也不受影响。

### 28.3 P2-8：`findResource` / `getResources` / `ServiceLoader`

`BfSecureLoader` 新增 `findResource(String)`，返回合成 `kboxbf:` URL；实现落在两个**显式注入**的
顶层类（不能是匿名内部类，否则要额外注入 `BfSecureLoader$1.class`）：

- `BfResourceHandler extends URLStreamHandler`
- `BfResourceConnection extends URLConnection`（`getInputStream` 才解码，流尽即擦）

配套的 native 侧新增两个**纯索引探测**（不解码、不产生明文窗口，因此不跑 `kbox_gateCheck()`，
避免每次 `findResource` 都做模块/JVMTI/调试器探测）：

- `hasResource(String)` → `g_res` 索引
- `hasClass(String)` → `g_classes` 索引

**Java 8 的坑**：`ClassLoader.findResources` 默认返回**空枚举**（只有 `URLClassLoader` 覆写它），
只覆写 `findResource` 时 `getResources(...)` 仍然看不到 blob → 必须同时覆写 `findResources`。

实测（`_hw/resprobe.jar`：`res/data.txt` + `META-INF/services/ResProbe$Svc`）：

```
stream=blob-resource-ok
url=blob-resource-ok          # Class.getResource(...).openStream()
resources=1 first=blob-resource-ok   # ClassLoader.getResources()
spi=impl-ok                   # ServiceLoader
```

### 28.4 P2-9：`java -cp` 启动

新增 CLI `--main-class` / 配置键 `mainClass`；打包器按情况生成两种引导：

1. **入口被改名** → 在**原名**写一个明文 stub：`main(String[])` 直接转发
   （BF → `BfSecureLoader.main`；有守卫 → `ResourceGuardLauncher.bootstrapCp`；
   纯改名 → 转发到改名后的 main）。stub 只引用引导类，验证/加载都不会碰到受保护字节码。
2. **入口未被改名但有守卫** → 在真实 `main` 头部注入
   `if (ResourceGuardLauncher.bootstrapCp(args)) return;`（COMPUTE_FRAMES 重算，帧安全）。
   `-jar` 路径已 `_booted`，落到真实方法体；`-cp` 路径第一次进入时完成引导并重新派发。

`BfSecureLoader` 同时改为**blob 优先**的 `loadClass`：blob 里有的类一定由它自己 define，
即使 jar 根上存在同名明文 stub（否则 parent-first 会拿到 stub 并无限递归）；hybrid 明文类不在
blob 中，仍走 parent。

`ManifestUpdater` 支持在**原本没有** Main-Class 时补写 `Main-Class` + `Original-Main-Class`
（必须写进主 section；追加到结尾空行之后会变成无 `Name:` 的第二节，JVM 报 `invalid manifest format`）。

## 29. P2-11 四类回归样本 + P3-15 BF 运行时改名

### 29.1 P3-15：BF 运行时表面按构建改名

旧产物里 `BfSecureLoader`（manifest Main-Class）、`BfInterpreter`、`com/kbox/runtime/bfvm/*`
都是明文类名，等于把方案直接写在产物上。现在每次构建生成一份随机映射
（[RuntimeRename.java](file:///d:/kboxobf/高级先行版源码/kbox-core/src/main/java/com/kbox/core/packaging/RuntimeRename.java)），
14 个 BF 专用类统一落到**同一个随机包**（1–2 字母包名 + 1–2 字母类名，同构建内唯一）：

```
BfSecureLoader / BfBlobInputStream / BfResourceHandler / BfResourceConnection /
BfInterpreter / BfInterpreter$BfRng /
bfvm/BfRuntime / bfvm/BfInterpreter / bfvm/VmCore(+Cursor/State/Uninitialized) /
bfvm/Opcode / bfvm/BfVmException
```

实现要点：

1. **一次生成、三端共享**：`ProtectionConfig.runtimeRenameMap`（transient，不解析配置文件）
   由 pipeline 在 BF 决策后生成，同时交给 `BfNativeBuilder` 和 `Packager`。
   自混淆（输入就是 kbox 自身）时跳过——graph 里已有这些类，只改注入副本会与 blob 引用脱节。
2. **字节级重写**：`RuntimeRename.remap` 用 ASM `ClassRemapper` + 自定义 `Remapper.mapValue`，
   除内部名/描述符/owner 外还改写 **字符串常量**（`Class.forName("com.kbox.runtime.BfSecureLoader")`
   出现在 NativeLoader / TamperShield / VmpInterpreter 中）。
3. **注入与 blob 同步**：`injectOne` / `injectBoot` / `collectOne` 用映射后的名字写条目/写 blob 键；
   `serialize()` 对所有应用类做一次 remap（VMP/BFVM 注入的 `BfRuntime.call`、
   hybrid 的 `BfSecureLoader.attach` 都在这时被改到新名字）。
4. **native 侧**：`BfNativeBuilder` 把映射后的内部名编译成 `KBOX_BF_LOADER_CLASS`，
   `JNI_OnLoad` 用它 `FindClass`；loader 方法哈希也改为对**改名后**的字节计算
   （改名会重排常量池 → code[] 里的 CP 索引变化，必须同源）。
5. **调用者门禁**：`BfSecureLoader.callerIsKbox` 原本硬编码 `"com.kbox.runtime."`，
   改名后会把 loader 自己的 `main()`/`<init>` 判成外部调用 → 改为按
   `BfSecureLoader.class` 自身包前缀判断（这也是所有 BF 类必须同包的原因）。

实测（`_hw/bf-full.conf`）：产物条目为 `y/n.class`、`y/w.class`、`y/l.class`、`y/x.class`，
`jar tf | grep -c "BfSecureLoader\|BfInterpreter\|bfvm/"` = **0**，`-jar` 与 `-cp` 均输出基线。
BF+JNIC+VMP（`bf-coexist.conf`）与纯 BFVM（`bfvm-only.conf`，bfvm 类落 `m/*`）同样运行正确。

### 29.2 P2-11：四类回归样本（可重复执行）

新增 `_hw/p211/`（源码 + `run.ps1`，ASCII-only 以兼容 PowerShell 5.1）：

| 样本 | 构造 | 断言 | 结果 |
|---|---|---|---|
| 无 Main-Class 库 | 只有 `app.Util.add(int,int)`，`jar cf` 无入口 | 产物**不得**出现 Main-Class/Original-Main-Class；外部 `LibCheck` 扫类 → 反射调用 `add(20,22)==42` | PASS（类被改名为 `app.a`） |
| SPI | `probe.Svc` + `ProvA/ProvB` + `META-INF/services/probe.Svc` | `ServiceLoader` 拿到 2 个实现（services 文件内容随改名同步） | PASS（`providers=2 names=AB`） |
| 签名 jar | keytool 生成 PKCS12 → jarsigner 签名 | 产物可运行；签名块被**剥离**（见下） | PASS（`signed-ok`） |
| multi-release | `probe.Main` 基版 + `META-INF/versions/17/probe/Main.class`，`Multi-Release: true` | JDK17 走 v17，JDK8 走 base | PASS（`version=17` / `version=base`） |

两个由样本暴露出的真实缺陷，一并修复：

1. **签名 jar 必然 `SecurityException`**：类字节被重写后 `.SF/.RSA` 里的摘要永远对不上，
   JVM 在 defineClass 时直接抛 `SHA-256 digest error`（实测复现）。
   修复：`Packager` 新增 `isSignatureFile()`，普通路径与 BF 路径都**丢弃**
   `META-INF/*.SF|*.RSA|*.DSA|*.EC`（ProGuard / Shadow / spring-boot repackage 的通行做法），
   并打印提示"如需签名请对产物重新签名"。MANIFEST 里残留的 `*-Digest` 在没有 `.SF` 时是惰性的。
2. **multi-release 版本化条目会覆盖基类**：`DependencyAnalyzer` 原先把
   `META-INF/versions/17/x/Main.class` 当普通类 `parseClass`，同一内部名后写覆盖先写，
   产物里基类直接变成 v17 字节（JDK8 也跑 v17）。
   修复：版本化条目**不进 graph**，作为原始资源透传（`isPlaintextStructural` 已覆盖
   `META-INF/versions/*`），同时把基类内部名记入 `ClassGraph.multiReleaseClasses`，
   pipeline 把这些类加入 keepPrefixes —— 版本化查找按**类名**进行，基类一旦改名，
   `META-INF/versions/17/<新名>.class` 就不存在了。

## 32. 2026-10-17 强度自测（StressApp）发现的 6 处真实缺陷与修复

用 `_hw/src/StressApp.java`（字符串/分支/循环/switch/try-catch/lambda/枚举/接口/数组/集合/递归）
在 `max.conf`（allMax + JNIC + VMP + BFVM + 原生壳）下做端到端自测，逐层定位并修复：

### 32.1 JNIC 方法运行期 `UnsatisfiedLinkError`（KboxListMask 误判）

`KboxListMask.unmaskText()` 的健全性检查要求解码结果含 `/`。默认包类名（`l`、`a$b`）没有包分隔符，
于是合法清单被判无效 → 调用方回落到“明文解析”把**密文当类名** → `isJnicClass("l")` 恒 false →
`RegisterNatives` 从未执行 → `UnsatisfiedLinkError: 'int l.y(int)'`。

修复：改为逐行校验“整行是合法内部类名”（允许默认包），并在 `readNameList()` 拒绝非可打印字节，
避免密文再次被当明文清单。实测 JNIC 方法恢复且结果与基线一致。

### 32.2 JNIC 解释器 `idiv/irem` 除零崩溃（EXCEPTION_INT_DIVIDE_BY_ZERO）

`kbox_jnic_interp_v3.c` 的 `IDIV/IREM` 直接做 C 除法；`safeDiv(1,0)` 在原生层触发 #DE，
进程以 `EXCEPTION_INT_DIVIDE_BY_ZERO (0xc0000094)` 崩溃（Java 语义应抛 `ArithmeticException`
并由方法自身的 exception table 捕获）。`INT_MIN / -1` 同样溢出。

修复：int/long 四种除法统一判零抛 `ArithmeticException("/ by zero")`，并特判 `MIN/-1`
（int 返回 INT_MIN、long 返回 LLONG_MIN、rem 返回 0）；待处理异常交由解释器主循环的
`kbox_try_dispatch` 走方法自己的 catch 表。实测 `div=42/-1` 与基线一致。

### 32.3 控制流平坦化长期“flattened 0 methods”（槽位模型错误）

`Flattener.stackEffect()` 对方法调用使用了 ASM `Type.getArgumentsAndReturnSizes()` 的原始值，
而该值**已包含隐式 `this`**：旧代码对实例调用再减 1、对静态调用直接用原值——两种情况都多弹 1 槽。
结果任何含调用的方法（`StringBuilder.append`、`Kind.values()`…）都以 `stack-underflow` 被拒。
另修：`NEWARRAY` 实际净效果是 0（旧值 +1）；短指令 `ILOAD_0..ASTORE_3` 补上槽位语义（防御手写节点）。

修复后 StressApp：`flattened 0 → 2 methods`（`build` 48→120 节点、`viaEnum` 44→93 节点）。
`main` 的 `cond ? a : b` 会把值跨块带到 GOTO（`fall-thru-stack`），属于当前 dispatcher
设计的真实限制，保持跳过。

### 32.4 MBA 两遍叠加击穿 64 KiB 方法上限 → 整类回滚

`mbaConstants` 先把常量展开成算术树，`mbaRewrite=5` 再对每个算术节点递归展开，`build` 从 351

原始字节（`PROTECTION DEGRADED`）。回滚只重映射符号引用，lambda 的 samMethodName 未同步 →
`AbstractMethodError: ... 'abstract int db(int,int)'`。

修复：
- `MbaRewriteObfuscator` 增加**实时预算**：单次展开后若 `insns + repl > 4000` 就保留原算术点；
- `Packager.FullRollbackRemapper` 增加 `mapInvokeDynamicMethodName`，让回滚类的 lambda 名字与
  接口 SAM 改名保持一致（与 `NameObfuscator.KBoxRemapper` 同逻辑）。

### 32.5 枚举类不再整体 keep（明文类名残留）

`WeaknessCatalog` 的 `ENUM_TYPE` / `AuditOrchestrator` 对每个枚举都发 `KEEP_CLASS`，

## 33. 2026-10-17 K-OTP：自写「原生种子一次性程序」+ 全功能回归

### 33.1 方案（K-OTP / Native-Seeded One-Time Program）

目标：让产物中**不存在稳定、可静态反编译的方法体**。与 VMP（固定虚拟化解释器）、
BFVM（Brainfuck 数据程序）不同，K-OTP 把方法体变成**一次一密**的 share：

```
构建期：
  P  = BfMethodCompiler.compile(method)              // BFVM 指令流
  A  = P XOR ks(seedNative, site, epoch=0, chain0)   // 只把 A 写进类文件
  state = long[]{epoch=0, chain=chain0}
  seedNative 只存在于 JNIC 原生库的常量里（库本身 KBNL + kboXShield 加壳）

运行期（每次调用）：
  P = A XOR ks(seedNative, site, epoch, chain)       // 还原到临时 byte[]
  r = VmCore.execute(P, ...)                        // 执行
  ng = mix(chain, site, epoch+1, nanoTime, tid, args) // 运行期熵
  A = P XOR ks(seedNative, site, epoch+1, ng)        // 就地重随机
  wipe(P); state = {epoch+1, ng}
```

- **信息论层面**：A 与 P 的关联完全由 native seed 决定；seed 不在 Java 侧，
  静态读到的 A 只是一段随机字节（2-of-2：A + native seed）。
- **每次调用后 A 都变化**：任何一次内存 dump 只对应一个已结束的 epoch，
  不存在可反复反编译的“程序快照”。
- **与其它层互补**：BFVM 吃掉 ≤1500 节点的小方法，K-OTP 接手 BFVM 跳过的
  大方法（本次 StressApp 的 `viaEnum` 9.3KB + lambda 5.1KB 指令流）。

### 33.2 接入点

- `com.kbox.core.otp.OtpMethodInjector`：选方法 → 编译 → 生成 share → 写
  `otpA$<site>` / `otpS$<site>` 字段与 `<clinit>` 初始化 → 方法体替换为
  `KotpRuntime.invoke(site, A, S, owner, self, args)` 薄桩。
- `com.kbox.runtime.KotpRuntime`：keystream（构建/运行共用）、native seed 绑定
  （复用 `registerNatives0`）、执行、重随机、擦除。
- `NativeCompiler`：JNIC 原生库新增 `Java_com_kbox_runtime_KotpRuntime_nativeSeed`
  + `registerNatives0` 里的 `KotpRuntime` 分组；seed 每构建随机。
- 流水线 Stage 31（BFVM 之后）：仅对未被 VMP/JNIC/BFVM 认领的方法生效；
  引擎类（`com/kbox/**`，含 renamePackages 后的 final 名）全部排除。
- 配置 `enableOtp`（`allMax` 自动开启；依赖 `enableJnic`）；GUI 增加
  “K-OTP 一次性程序（需 JNIC）”开关。

### 33.3 实现期发现的缺陷

1. **桩描述符写错**：`(I[BL[J...)` 多了一个 `L`，`L[JLjava/lang/Class;` 被
   当成类名 → `VerifyError` / 整类回滚。修正为 `(I[B[J...`，并用独立 ASM
   校验桩验证通过。
2. **误选引擎诱饵类**：S4 honeypot 在 renamePackages 后变成 `d/e/f/*`，
   `startsWith("com/kbox/")` 失效 → OTP 注入诱饵类导致 VerifyError。
   现在按 `classMap` 中 `com/kbox/**` 的 **final 名**排除。
3. **原生库缺少前向声明**：`registerNatives0` 引用 `nativeSeed` 但定义在后，
   gcc 报 undeclared；补 `JNIEXPORT jlong ...(JNIEnv*, jclass);`。
4. **BF/非 BF 两条注入路径**都要带上 `KotpRuntime` 与 bfvm 运行时
   （plaintext `injectRuntimeClasses` + BF `collectRuntimeClassesForBlob`）。
5. **VmCore 丢失 checked throwable 类型**：K-OTP 虚拟化的方法里若含
   TypeConfusion 的 relay carrier（非 RuntimeException/Error），`ATHROW`/反射调用
   会被包装成 `BfVmException`，导致方法自身的 catch 表匹配不到 carrier → 
   `ATHROW of non-runtime throwable`。改为 `sneakyThrow` 原样抛出，让解释器的
   异常表按真实类型分派（uncaught 时也保留原类型）。此修复同时提升 BFVM 的
   异常语义兼容性。

### 33.5 诚实的强度边界

K-OTP 不是“数学上不可逆”：解码器就在产物里，攻击者若完整逆向 native 库并
在每次调用时截获临时 P，仍可恢复单个 epoch 的程序。它做到的是：
**静态产物中没有可反编译的稳定方法体；每次调用后磁盘/内存中的 share 都已重随机；
单独 dump 只能得到一个已失效的 epoch。** 配合 native 壳（KBNL + kboXShield）
把 seed 的获取成本抬到“先破壳”的级别。

## 34. 适配性增强：字符串全乱码根因、反射改名、InnerClasses、BF 打包类

本轮用 Java 21 特性样本（record / sealed + pattern switch / enum switch /
自定义序列化 / 反射 / VarHandle / SPI / 文本块 / indy concat）与 Java 8 样本做
全开（`_hw/max.conf`）与 BF 全开（`_hw/allmax.conf`）回归，修掉 5 个真实缺陷。

### 34.1 根因：崩溃日志残留误报 → 所有字符串解密成噪声

现象：`Hi21` 输出 `I?uF?&?~1 / ?lr?jNa`，`StressApp` 全乱码；但直接反射调用
holder 解密器能正确解出 `hello21=`，构建期与运行期 keyfp 完全一致。

定位：`AntiDebug.checkCrashDumpResidue()` 扫描 `java.io.tmpdir`，只要看到
`hs_err_pid*` / `replay_pid*` / `java_pid*` / `*.hprof` 就把 `tampered=true`。
本机 18:02 有一次无关 JVM 崩溃留下 `hs_err_pid158864.log`，此后**每一次**运行
都被判为被调试，解密器走噪声分支（返回密文前 8 字节的 UTF-8），程序继续跑但
字符串全废。这也解释了此前“关掉 antiDebug 仍乱码”：`ResourceGuardLauncher`
无条件调用 `AntiDebug.check()`。

修复：

1. 残留扫描只认可**当前进程 PID** 的转储（`hs_err_pid<pid>` 等），
   其他 JVM 的历史崩溃日志一律忽略。
2. 计时金丝雀阈值放宽：单轮 wall > 50ms（原 5ms）、wall/cpu 比 > 20 且
   wall > 250ms（原 10ms）才判定被单步/挂钩——原阈值在高负载机器上
   会把普通调度抖动当成调试器。
3. AES 解密器的 `if (AntiDebug.isTampered()) goto noise` 改为**按构建配置生成**：
   `antiDebug=false` 的产物里不再有这条分支，其他组件置位的 tamper 标志
   不会再把正常业务字符串污染成噪声。

### 34.2 反射字符串常量未随类改名

`ClassRemapper` 只改符号引用，改不到 `Class.forName("a.b.C")` 里的字符串。
`CompatApp` 的 `Class.forName("compat.ReflectTarget")` 在改名后
要么 `ClassNotFoundException`，要么被反射门以 `SecurityException("KBox")` 拒绝
（白名单按新名算哈希）。

修复：`NameObfuscator.apply()` 增加预处理 `rewriteReflectionStringConstants`，
按 rename map 精确改写 `LDC` 字符串的三种文本形式：内部名 `a/b/C`、
点分名 `a.b.C`、字段描述符 `La/b/C;`。不匹配的字符串保持原样。
这一条同时覆盖 `ClassLoader.loadClass`、`getResourceAsStream("a/b/C.class")`
等所有“以字符串指定类”的 API。

### 34.3 InnerClasses 不能单独擦除（record toString / getSimpleName）

`eraseSignatures` 原先直接 `cn.innerClasses = null`。Java 21 的 record
`toString` 走 `ObjectMethods.makeToString` → `Class.getSimpleName()`：
嵌套 record 丢失 InnerClasses 后会把简单名退化成二进制名（实测
`CompatApp$Point[x=3, y=4]`，基线是 `Point[x=3, y=4]`）。

只保留“描述自身”的条目也不行：JVM 会在内外类之间做一致性校验，只让一侧
保留条目会抛

```
IncompatibleClassChangeError: compat.CompatApp and compat.CompatApp$Point
disagree on InnerClasses attribute
```

结论：`InnerClasses` 必须**整体保留或整体删除**二选一。这里选择保留——
它只把已经混淆过的名字连成嵌套关系，泄露的信息量极低，而
`getSimpleName()` / `getDeclaringClass()` / record `toString` /
Jackson `@JsonTypeInfo(NAME)` 都依赖它。`EnclosingMethod` 仍按原策略擦除。

### 34.4 BF 打包：`hasClass` 收到点分名 → 入口 stub 无限递归

`BfSecureLoader.loadClass(name, resolve)` 把 JVM 传来的**二进制名** `compat.CompatApp`
直接交给原生 `hasClass`，而 BF 索引按**内部名** `compat/CompatApp` 建表。
默认包（`HelloWorld`、`h`）没有点号，所以此前所有 BF 回归都恰好通过；
一旦主类在具名包里，`hasClass` 恒 false → 回落到父加载器 → 拿到 packer 写在
原主类名上的明文 `-cp` stub → `BfSecureLoader.main` → 再加载 → 无限递归
（`InvocationTargetException` 嵌套上千层，最终 StackOverflow）。

修复：`loadClass` 调用 `hasClass(name.replace('.', '/'))`。

### 34.5 回归矩阵（全部与未混淆基线逐行 diff）

### 35.3 为通过测试修掉的真实缺陷

1. **1.8.9/1.12.2 的 `mcmod.info` 未被识别**：检测器只认 fabric.mod.json /
   mods.toml，老 Forge Mod 完全没走 MC 适配。补 `mcmod.info` 分支（保留
   `mcmod.info`，把每个带 `@Mod` 的类加入 keep）。
2. **`@Mod` 的 modid 属性**：只读了 `value`，而 Forge 1.8.9–1.20 写的是
   `@Mod(modid="...")` → 入口类识别为 0。改为同时接受 `modid`/`value`。
3. **类加密与 Mod 加载器冲突**：FML/NeoForge 在定义任何类之前会 ASM 扫描 jar 内
   **每一个** `.class` 找 `@Mod`；被 AES 加密的条目直接让整个 jar 被判为
   "corrupt zip"。检测到 Mod 时自动关闭 `encryptClasses`。
4. **反反编译器的畸形属性**：level 2/3 会写入假的 StackMapTable / 非法常量池引用，
   同样让加载器的全量扫描失败。检测到 Mod 时自动把 `antiDecompiler` 降为 0。
5. **BF blob 与宿主加载器不共存**：hybrid 模式把引擎类藏进 blob，而 Mod 类是宿主
   加载器定义的明文类，引用 `VmpInterpreter` 时 `NoClassDefFoundError`。Mod jar
   自动降级为非 BF（其余保护保留）。
6. **VMP 的解释器侧类解析**：Gson `ExclusionStrategy` 用 `Class ==` 判断，VMP 下
   会得到不同 Class 实例而静默走错分支。Mod jar 自动关闭 VMP（可执行程序仍全开）。
7. **资源混淆与 Mod 资源查找冲突**：`ResourceBundle.getBundle("luckperms")`、
   `assets/**`、`data/**` 都按原路径读取。Mod jar 自动关闭 `obfuscateResources`。
8. **Fabric `fabric.mod.json` 解析器把"值"当"键"**：`"environment": "server"`
   里的 `"server"` 被当成 entrypoints 的 `server` 键 → 入口类 0 个、
   `LPFabricBootstrap` 被改名后 `ClassNotFoundException`。新增
   `indexOfJsonKey`（只匹配后跟 `:` 的键）。
9. **JDK 接口方法被改名**：`ListeningList implements java.util.List` 的
   `iterator()` 被改成 `gr()` → `AbstractMethodError`。`RetentionDecision` 现在
   用 `Class.isInterface()` 判断所有 `java/*` 类型，任何 JDK **接口**的覆写方法
   一律保名（JDK 类仍跳过，避免 Object 把全 jar 方法都锁死）。
10. **回滚类的名字映射混用原名/新名**：序列化失败回滚时，`FullRollbackRemapper`
    走父类链用的是"新名 ClassNode 的新 superName"，而映射表以原名索引 →
    父类方法查不到，调用点保留 `get`、声明已改成 `jzd` → `NoSuchMethodError`。
    现在每一跳都先 `reverseClassMap` 归一化回原名。
11. **BFVM 三处**：
    - 重建方法体时丢弃注解 → Mixin `@Overwrite/@Inject` 消失，
      `InvalidMixinException: contains non-private static method`。改为完整复制
      注解/参数注解/签名/异常表。
    - `allInterfaces` 只看运行时类的直接接口，漏掉父类实现的 `Collection.stream`
      → `method not found: SingletonImmutableList.stream()`。改为遍历所有父类的
      接口。
    - `findField` 同样补接口常量查找。
12. **JNIC 的急切类解析**：方法入口把常量池里的类全部 `FindClass`，专用服务器上
    缺失的客户端类即使所在分支永不执行也会让整个方法失败。改为：入口解析失败
    清异常置 NULL；`LDC class` 真正执行时才抛 `NoClassDefFoundError`；解析优先
    使用声明类的 loader（`kbox_find_class`），与 JVM 语义一致。
